================================================================================
CUS -- Core-Wasm Unit Scripts
Design proposal for review
================================================================================

Status:   proposal, nothing implemented
Author:   Claude (Gravitas/ToTheLastDrop port)
Scope:    lets unit scripts be written in Rust/WASM instead of Lua (LUS) or COB
Goal:     full functional parity with springcontent's unit_script.lua gadget

Naming: LUS = Lua Unit Script. CUS = Core-wasm Unit Script, by analogy.

All engine paths below are in the spring-bar checkout. Line numbers are from the
revision this was written against (47def3ba27) and are indicative.

--------------------------------------------------------------------------------
0. WHY THIS IS SMALLER THAN IT LOOKS
--------------------------------------------------------------------------------

Two findings that shape the whole design. Both verified by reading the engine.

(a) UnitScriptFactory is NOT the extension point.

    CUnitScriptFactory::CreateScript (rts/Sim/Units/Scripts/UnitScriptFactory.cpp:29)
    returns CNullUnitScript for anything whose scriptName is not *.cob. Its own
    comment says Lua scripts are "deferred to LuaUnitScript::CreateScript". The
    real attachment happens later, from the gadget, via the callout
    Spring.UnitScript.CreateScript(unitID, callInTable)
    (rts/Sim/Units/Scripts/LuaUnitScript.cpp:1163), which does:

        unit->script = CUnitScriptFactory::CreateLuaScript(unit, L);

    So CUS attaches the same way: a guest calls a create-script callout at
    UnitCreated time. The factory needs no new branch and no new file format.

(b) The coroutine/threading model is NOT in the engine.

    Spring.UnitScript.WaitForTurn/WaitForMove/WaitForScale return a plain
    "needsWait" boolean (LuaUnitScript.cpp:1882+). AnimFinished
    (LuaUnitScript.cpp:933) just dispatches TurnFinished/MoveFinished/
    ScaleFinished callins. Everything else -- StartThread, Sleep, Signal,
    SetSignalMask, the blocking behaviour of WaitFor*, the sleeper queue, the
    per-unit thread registry -- lives entirely in
    cont/base/springcontent/LuaGadgets/Gadgets/unit_script.lua (842 lines).

    Therefore CUS owns its scheduler in Rust. The engine needs no scheduler, no
    coroutine support, and no guest suspension. This is the single most important
    point for reviewers: guests cannot yield mid-callin, and they do not need to.

(c) Animation stepping is already engine-side and costs nothing extra.

    CUnitScriptEngine::Tick -> TickAllAnims runs every sim frame, multithreaded
    via for_mt (rts/Sim/Units/Scripts/UnitScriptEngine.cpp:139). Scripts only
    START animations and get *Finished callbacks. CUS inherits this for free.

(d) Call frequency is low. This is not a per-frame-per-unit dispatch.

      AimWeapon          gated by reaimTime = GAME_SPEED>>1 = 15 frames
                         => at most ~2x/sec per weapon (Weapon.cpp:380,423)
      ChangeHeading      per frame while turning, gated by minScriptChangeHeading
      QueryWeapon        only on weapon-piece updates (Weapon.cpp:241)
      AimFromWeapon      only on weapon-piece updates (Weapon.cpp:244)
      *Finished          only when an animation completes
      everything else    event-driven (Create, Killed, Activate, StartMoving,
                         FireWeapon, Shot, HitByWeapon, Destroy, ...)

--------------------------------------------------------------------------------
1. PART A -- ENGINE WORK
--------------------------------------------------------------------------------

A1. New class CNativeUnitScript : public CUnitScript
    Location: rts/Sim/Units/Scripts/NativeUnitScript.{h,cpp}

    Named for the NativeInterface layer, not for wasm: native shared-library
    modules and Core-WASM guests both reach the engine through NativeInterface,
    so one class serves both and the wasm host becomes just one dispatch backend
    behind it. Do not call it CWasmUnitScript.

    Model it on CLuaUnitScript. It must implement the ~45 pure virtuals declared
    in rts/Sim/Units/Scripts/UnitScript.h:171-220 and forward each to the owning
    guest module. Like CLuaUnitScript it should track which callins the guest
    actually provides, so absent ones cost nothing (see HasBlockShot /
    HasTargetWeight / hasSetSFXOccupy / hasRockUnit / hasStartBuilding).

    The 40 callin slots, from rts/Sim/Units/Scripts/LuaScriptNames.h:

      Destroy StartMoving StopMoving StartSkidding StopSkidding ChangeHeading
      Activate Killed Deactivate WindChanged ExtractionRateChanged RockUnit
      MoveRate setSFXoccupy HitByWeapon QueryLandingPads Falling Landed
      BeginTransport QueryTransport TransportPickup StartUnload EndTransport
      TransportDrop StartBuilding StopBuilding QueryNanoPiece QueryBuildInfo
      MoveFinished TurnFinished ScaleFinished QueryWeapon AimWeapon AimShield
      AimFromWeapon FireWeapon EndBurst Shot BlockShot TargetWeight

    Callins with return values the sim consumes synchronously (QueryWeapon,
    AimFromWeapon, QueryTransport, QueryNanoPiece, QueryBuildInfo, BlockShot,
    TargetWeight, QueryLandingPads) must return through the call, not via a
    later callout. These are not all scalars: QueryLandingPads fills a
    std::vector<int> (UnitScript.h:185), so the dispatcher needs a typed result
    union plus a capacity/retry contract for list results.

    Storage constraint, raised by codex and verified: unit scripts are placement-
    new'd into a fixed inline buffer.

        rts/Sim/Units/Unit.h:303           uint8_t usMemBuffer[sizeof(CLuaUnitScript)];
        UnitScriptFactory.cpp:52,59        static_assert(sizeof(X) <= sizeof(usMemBuffer))

    CNativeUnitScript must either fit inside sizeof(CLuaUnitScript) or the buffer
    must be resized (it is per-CUnit, so growing it costs memory on every unit in
    the game). Keep the C++ object thin -- module handle, instance id, provided-
    callin mask -- and hold all real state guest-side. A factory method
    CreateNativeScript(unit, module, instance) belongs next to CreateLuaScript;
    the factory needs no new extension-sniffing branch, but it does need this.

A2. Dispatch transport -- REVISED, option 2 wins

    An earlier draft preferred one multiplexed callin on extensibility grounds.
    That was the wrong criterion for a hot path. Corrected:

    Use 40 discrete, typed callin exports.

    Why it is faster:
      - Each export has a fixed, statically known signature. Args decode straight
        from the scratch wire with no variant tag and no union.
      - No callin-id switch in the guest; the callin identity is compile-time, so
        the whole handler monomorphises and inlines.
      - A multiplexed callin forces the widest argument payload on every event
        (HitByWeapon's floats, ChangeHeading's short, TransportDrop's float3),
        so cheap frequent events pay for expensive rare ones.
      - 40 registry entries is a codegen cost paid once, not a runtime cost. The
        Core set already carries 132 callins.

    Codex's architectural objection stands independently and is accepted: these
    must NOT live in the general module-wide rules-callin dispatcher, because
    unit scripts are per-instance objects with different lifetime and routing.
    The two concerns are compatible -- put the 40 discrete typed exports in their
    own namespace ("spring:unit-script-callin/..."), routed by
    CNativeUnitScript through its own dispatcher, separate from
    WasmInterfaceSystem::DispatchActiveCoreCallin.

    Every callin also carries the script-instance id, not just the unit id, so
    routing is an array index rather than a lookup.

    Provided-callin mask: create-script passes a u64 bitmask of the callins the
    script actually implements. CLuaUnitScript already does the equivalent
    (hasRockUnit, hasStartBuilding, hasSetSFXOccupy, HasBlockShot,
    HasTargetWeight). With tens of thousands of units this is the difference
    between zero host->guest crossings and tens of thousands per event type.

A3. New callout module "spring:unit-script" (currently has only call-unit-script)
    Mirror the Lua surface registered at LuaUnitScript.cpp:1047-1093.

    Attachment / lifecycle:
      create-script(unitID, providedCallinMask)   <- replaces unit->script
      update-call-in(unitID, callinId, present)
      set-death-script-finished(unitID, wreckLevel)

    Animation. Expose EXACTLY the LUS-visible set for v1 parity. Verified against
    REGISTER_LUA_CFUNC in LuaUnitScript.cpp:1047-1093 -- MoveNow, TurnNow,
    ScaleNow and Shatter are methods on CUnitScript but are NOT registered Lua
    callouts, so an earlier draft was wrong to list them as LUS surface. Adding
    them is a separate compatibility decision, not parity work.

      move / turn / spin / stop-spin / scale
      is-in-move / is-in-turn / is-in-spin / is-in-scale
      wait-for-move / wait-for-turn / wait-for-scale   (return needsWait bool)

    Pieces / effects:
      set-piece-visibility
      emit-sfx, explode, show-flare
      attach-unit, drop-unit
      get-piece-translation / get-piece-rotation / get-piece-scale
      get-piece-pos-dir

    The Multi* forms ARE registered Lua callouts, but they are implemented in
    LuaUnitScript.cpp as loops over the singular operation, not as CUnitScript
    methods. Implement them as Rust Ctx helpers over the singular callouts; do
    not add engine callouts for them.

    COB interop:
      get-unit-value / set-unit-value
      get-unit-cob-value / set-unit-cob-value

A3b. CallAsUnit / GetScriptEnv -- RETRACTED, this is a hard requirement

    An earlier draft claimed CallAsUnit and GetActiveUnitID were "not needed"
    because they only exist to serve Lua's implicit active-unit stack. That was
    wrong, and it would have broken shipping games. Gadgets routinely drive unit
    animation on demand through this pair. Verified usages in this repo alone:

      LD43.sdd/LuaRules/Gadgets/api_blood_magic.lua:178,219,248,278,309,316
          CallAsUnit(unitID, env.script.CastAnimation, ...) and StopMoving
      LD43.sdd/LuaRules/Gadgets/unit_status_effects.lua:41,58
          env.script.Buff(duration), env.script.Stun(duration)
      Hunted.sdd/LuaRules/Gadgets/unit_mine.lua:45
          env.StartFuse
      Hunted.sdd/LuaRules/Gadgets/unit_attributes.lua:197
          env.script.StopMoving(hx, hy, hz)

    So CUS must let a rules guest invoke a named entry point on a specific unit's
    script, with arguments and return values, running under that script's thread
    context. Scripts therefore need custom entry points beyond the 40 engine
    callins -- in LUS these are simply extra functions in env.script.

    Good news: the callout already exists. spring:unit-script/call-unit-script is
    the wasm equivalent of CallAsUnit + GetScriptEnv (NativeCallUnitScript,
    SyncedCtrl.cpp:6449) -- named function, args, return values. It is currently
    hardcoded to Lua:

        CLuaUnitScript* script = dynamic_cast<CLuaUnitScript*>(unit->script);
        if (script == nullptr) { ... "Unit is not running a Lua unit script" }

    The engine work is to lift CallFunctionByName onto CUnitScript (or a small
    shared interface) so CNativeUnitScript answers it too. That is a smaller
    change than adding a new callout, and it makes CUS a drop-in for gadgets that
    already use this pattern.

    On the remaining half of the point, codex is right and the draft was right:
    a CUS script should not be able to animate arbitrary units. Ctx should own an
    opaque script-instance handle and scope all animation/piece/effect operations
    to that instance's unit. Cross-unit operations stay only where LUS already
    allows them (AttachUnit/DropUnit). Explicit instance scoping replaces the
    activeUnitStack; it does not replace CallAsUnit.

A4. Weapon indexing
    LuaConfig.h:8 sets LUA_WEAPON_BASE_INDEX 1, and LuaUnitScript's *Weapon*
    callins supply 1-based indices. CUS must be 1-based too, for consistency with
    the rest of the wasm surface after commit 47def3ba27.

A5. Sync safety
    Unit scripts are synced. Iteration order over guest-side thread collections
    must be deterministic -- the Lua gadget explicitly warns that its threads
    table is keyed by coroutine and "careless iteration WILL cause desync". A
    Rust port must use ordered containers (Vec, BTreeMap), never HashMap
    iteration, anywhere a decision affects sim state. Call this out in review.

--------------------------------------------------------------------------------
1B. PART A2 -- ENGINE CONTRACTS RAISED IN REVIEW (all accepted)
--------------------------------------------------------------------------------

    Module lifetime / unload. WasmCoreHost owns host objects only until its
    module unloads. Every CNativeUnitScript must carry a checked module/instance
    reference, and unload must detach or replace all scripts before that
    reference dies. A faulted script needs a deterministic fallback (revert to
    CNullUnitScript, keep the unit alive).

    Save/load. CUnitScript participates in creg serialization. A guest heap and
    pending scheduler state cannot be recovered implicitly. Either declare CUS
    explicitly non-saveable in milestone 1, or design guest state serialization
    into the first API. This interacts directly with the scheduler choice in 2B.

    Re-entrancy. The scheduler being guest-side does not remove the re-entry
    problem: a script can call an engine import that itself triggers a unit-
    script callback, and re-entering the same Wasmtime store before the import
    returns is not valid. Needs a per-module dispatch guard -- queue async
    callbacks raised during execution, drain at a safe engine boundary in
    deterministic order, and reject (or design a non-reentrant engine path for)
    callins whose C++ caller demands a synchronous result.

    AimWeapon / AimShield are void. CUnitScript::AimWeapon and AimShieldWeapon
    return void (UnitScript.h:214-215). The bool in the script-facing trait is
    published asynchronously via SetUnitWeaponState(..., "aimReady", 1.0/0.0)
    and SetUnitShieldState, exactly as the Lua wrapper does. The engine never
    consumes a synchronous bool -- the trait sketch in Part C must not imply it.

    Killed cannot rely on Rust Drop. A Wasmtime trap gives no reliable guest
    unwind point. CNativeUnitScript must guarantee
    CUnit::KilledScriptFinished(defaultWreckLevel) from C++ whenever a missing,
    faulted, or non-settling CUS Killed handler fails to finish the death.

1C. PERFORMANCE BUDGET -- THE DESIGN CONSTRAINT
--------------------------------------------------------------------------------

    Target: tens of thousands of units, still fast. COB is still used over LUS
    precisely because LUS costs coroutine creation, table lookups and pcall per
    event. CUS has to beat LUS decisively or it will not get adopted.

    The governing principle: an idle unit must cost ZERO per frame.

    Nothing in this design iterates over all units. Animation stepping is already
    engine-side and multithreaded (TickAllAnims, UnitScriptEngine.cpp:139); CUS
    inherits it. The only per-frame guest work is draining tasks that are due.

    P1. One frame crossing, not N.
        A single per-frame callin drains the wake queue inside the guest, exactly
        as the Lua gadget's GameFrame does. Never a per-unit tick. With 10k units
        and 20 waking tasks this is 1 crossing, not 10000.

    P2. Provided-callin mask (A2) means absent callins cost nothing at all --
        no crossing, no dispatch, no guest entry.

    P3. No per-unit heap allocation, no dyn dispatch on the hot path.
        Box<dyn UnitScript> per unit is 10k allocations plus a vtable hop per
        event. Instead, storage is per script TYPE:

          registry:  Vec<TypeVTable>              one entry per script type
          per type:  Vec<S>                       contiguous state, S concrete
          index:     Vec<ScriptRef> by unit id    ScriptRef { type: u16, slot: u32 }

        Unit ids are dense and bounded in Spring, so the index is a direct array
        subscript -- no hashing anywhere. 8 bytes x 32k units = 256 KB, trivial.
        Within a type, dispatch is monomorphised and inlines.

    P4. Threads: most units have zero, and must cost zero.
        Per script type: Slab<Task<S::Thread>> with generational ids. Per
        instance: threads_head: Option<TaskId>, an intrusive singly-linked list
        through the slab. No per-unit Vec, no allocation for the common
        zero-or-one thread case.

    P5. Sleepers: timer wheel, not BTreeMap.
        Sleep(ms) becomes max(1, ms/33) frames, and real sleeps are short. A ring
        of buckets indexed frame & (N-1) (N = 256) gives O(1) insert and O(woken)
        per frame with no allocation in steady state. An overflow Vec handles the
        rare long sleep. A BTreeMap<frame, Vec<..>> allocates per distinct frame
        and costs a tree descent per insert -- wrong structure for this.

        (This supersedes the BTreeMap suggestion in an earlier draft.)

    P6. Wait queues: intrusive, not mapped.
        Store the wait key (piece*3+axis, or piece for scale) inside the Task and
        walk the unit's own short task list on MoveFinished/TurnFinished/
        ScaleFinished. Typical units have <= 4 live threads, so a linear walk
        beats any map, and there is nothing to allocate or hash.

    P7. Signal is a walk of one unit's task list.
        O(threads on that unit), testing bit_and(mask, signal_mask) for numeric
        masks and equality otherwise. No global scan.

    P8. Determinism is not negotiable and costs nothing here.
        Every structure above is ordered by construction (Vec, slab index order,
        wheel bucket order). No HashMap iteration anywhere that affects sim
        state. The Lua gadget explicitly warns its coroutine-keyed thread table
        would desync if iterated carelessly; CUS avoids the hazard structurally.

    Expected steady-state cost per frame: one host->guest call, one wheel bucket
    index, and a walk of only the tasks actually due. Units with no live thread
    are never touched.

2. PART B -- THE CUS RUNTIME IN RUST
--------------------------------------------------------------------------------

Copy-pasted into each game first; extracted to a crate (spring-cus) once two or
three games use it. Suggested layout, matching the house style (thin mod.rs,
step-down ordering, no comments):

    cus/mod.rs          pub use only
    cus/runtime.rs      per-unit registry, callin entry point, dispatch
    cus/thread.rs       cooperative threads, signals, sleep, wait queues
    cus/anim.rs         move/turn/spin/scale wrappers + WaitFor*
    cus/piece.rs        piece name -> id resolution, show/hide
    cus/script.rs       the UnitScript trait games implement

B1. The scheduler -- state machines vs async, decided on measurement grounds

    Rust guests cannot yield mid-callin, so Lua coroutines do not port directly.
    Both candidate models compile to state machines; the difference is who writes
    the machine and what you can do with it afterwards.

    Perf: they are equivalent, and neither needs to allocate.
      An async fn compiles to a compiler-generated state machine struct of known
      size. If futures are stored INLINE in the per-type slab (P3/P4) rather than
      boxed, polling is a direct monomorphised call -- no allocation, no dyn, no
      waker indirection if the executor is hand-rolled for this one use. So
      "async is slower" is not true here, provided nothing is boxed. The only
      real cost is size: a future holds every local alive across an await, so
      Task<S::Thread> is wider than a hand-written enum with minimal state. That
      matters at 10k+ units, and is the one measurable argument for hand-rolling.

    Expressiveness: async wins clearly.
      Gravitas' scripts are 34 Turn, 29 Sleep, 23 StartThread calls of
      straight-line animation sequencing. Written as explicit state machines that
      becomes an enum with a state per await point, by hand, per script. That is
      the "penalty to usability/expressability" to avoid. Async keeps the code
      shaped like the Lua original.

    Serialization: explicit state machines win, decisively.
      A compiler-generated future cannot be serialized. If CUS must support
      save/load, async is out unless save/load is handled by replaying rather
      than snapshotting. Codex recommends explicit state machines largely on this
      basis, plus cancellation and debuggability.

      On cancellation specifically: Signal under async is just dropping the
      future, which is clean and correct. That objection is weaker than the
      serialization one.

    Three options, ranked:

      Option A -- async, inline-stored, save/load declared out of scope for v1.
        Best expressiveness, equal speed, smallest amount of new machinery to
        write. Needs a hand-rolled no-alloc executor and a per-type enum of
        concrete thread futures so nothing is boxed. Blocks saveability.

      Option B -- explicit state machines.
        Serializable, debuggable, smallest per-task memory. Costs real
        ergonomics on exactly the scripts that matter most.

      Option C -- proc macro generating an explicit, serializable state machine
        from straight-line syntax.
        Gets both. Costs a proc macro to write and maintain, and worse compile
        errors. This is what COB effectively is: sequential source, machine
        underneath.

    Recommendation: decide save/load FIRST, because it decides this. If CUS may
    be non-saveable in v1, take A and keep C as the migration path (the script-
    facing syntax is nearly identical, so A->C is not a rewrite of game scripts).
    If saveability is required from day one, take B for the vertical slice and
    move to C before porting anything the size of gravit.lua.

    Either way the public trait should be written so game scripts do not change
    shape between A and C. That is the property worth protecting.

    Per-unit state, either way:
      threads_head    Option<TaskId>              intrusive list head
      wait key        stored in Task, not a map
      sleepers        global timer wheel, not per unit

B2. Exact semantics to reproduce (from unit_script.lua)

    Sleep(ms)
      n = floor(ms / 33); if n <= 0 then n = 1; wake at GetGameFrame() + n.
      Note the 33, not 30 -- do not "fix" this, it changes timing.

    StartThread(fun, ...)
      Runs IMMEDIATELY (unlike COB, which defers to first schedule). The gadget
      documents this divergence and keeps it. signal_mask is INHERITED from the
      currently running thread, else 0.

    SetSignalMask(mask)
      Sets the mask on the currently running thread only.

    Signal(mask)
      Number mask: kill every thread where bit_and(signal_mask, mask) ~= 0.
      Non-number mask: kill every thread where signal_mask == mask (equality).
      Only threads currently in a container (sleeping or waiting) are removed;
      a running thread is not killed by its own Signal.

    WaitForMove/WaitForTurn/WaitForScale
      Ask the engine first (needsWait bool). Only block if true. Key is
      piece*3+axis for move/turn, plain piece for scale.

    MoveFinished/TurnFinished/ScaleFinished/Destroy
      Framework-owned. They OVERWRITE any script-provided version -- games must
      not define them. On fire, wake ALL threads queued on that key, popping from
      the end, tolerating mutation of the queue during iteration.

    Killed
      Wrapped so that SetDeathScriptFinished(wreckLevel) is ALWAYS called, even
      on error (the gadget uses SetOnError for exactly this). The callin returns
      nothing, which tells the engine to wait for that call. Getting this wrong
      leaves corpses permanently mid-death.

    AimWeapon
      Wrapped in a thread; result feeds
      SetUnitWeaponState(unitID, weaponNum, "aimReady", 1.0 or 0.0).

    AimShield
      Wrapped in a thread; result feeds
      SetUnitShieldState(unitID, weaponNum, bool).

    Create
      NOT called by the engine. The framework starts it in a thread after
      registration. Easy to miss.

    Thread-wrapped callins (verbatim list from the gadget; the commented-out
    ones are deliberately NOT wrapped):
      RockUnit, Falling, Landed, BeginTransport, TransportPickup, StartUnload,
      EndTransport, TransportDrop, StartBuilding, StopBuilding, FireWeapon
      plus always-wrapped: Create, Killed, AimWeapon, AimShield

    Per-weapon dispatch
      If AimWeapon is absent but AimWeapon1 is present, build a dispatch table
      from Name1..NameN over ud.weapons for each of:
      QueryWeapon AimFromWeapon AimWeapon AimShield FireWeapon Shot EndBurst
      BlockShot TargetWeight
      Missing entries fall back to these defaults:
        QueryWeapon = -1, AimFromWeapon = -1, AimWeapon = false,
        AimShield = false, BlockShot = false, TargetWeight = 1

    Hide(piece) / Show(piece) = SetPieceVisibility(piece, false/true)

    GetLongestReloadTime(unitID)
      Scans weapon indices 1..32, returns 1000 * max reloadTime.

B3. What does NOT carry over
    - env/_G per-unit global table: Rust scripts hold their own struct state.
    - include()/MemoizedInclude: Rust modules.
    - piece(...) name lookup: resolve once at Create via get-unit-piece-map,
      store ids in the script struct. Gravitas alone has 117 piece() calls, so
      this is the single biggest ergonomic win available.
    - script loading by filename with .cob->.lua fallbacks: replaced by an
      explicit registration table (see Part C).
    - weak thread table / GC: use explicit removal on completion.

3. PART C -- HOW A GAME IMPLEMENTS IT
--------------------------------------------------------------------------------

C1. The trait each unit script implements (sketch, Model B flavour)

    pub trait UnitScript {
        fn create(&mut self, ctx: &mut Ctx) {}
        fn killed(&mut self, ctx: &mut Ctx, recent_damage: f32, max_health: f32) -> i32 { 0 }
        fn aim_weapon(&mut self, ctx: &mut Ctx, weapon: i32, heading: f32, pitch: f32) -> bool { false }
        //   ^ script-facing only. CUnitScript::AimWeapon is void; the runtime
        //     publishes this via SetUnitWeaponState(unit, weapon, "aimReady", ..)
        //     asynchronously, exactly as the Lua wrapper does.
        fn query_weapon(&mut self, ctx: &mut Ctx, weapon: i32) -> i32 { -1 }
        fn aim_from_weapon(&mut self, ctx: &mut Ctx, weapon: i32) -> i32 { -1 }
        fn fire_weapon(&mut self, ctx: &mut Ctx, weapon: i32) {}
        fn activate(&mut self, ctx: &mut Ctx) {}
        fn deactivate(&mut self, ctx: &mut Ctx) {}
        fn start_moving(&mut self, ctx: &mut Ctx, reversing: bool) {}
        fn stop_moving(&mut self, ctx: &mut Ctx) {}
        fn hit_by_weapon(&mut self, ctx: &mut Ctx, x: f32, z: f32, weapon_def: i32, damage: f32) -> f32 { damage }
        ...
    }

    Defaults mirror default_return_values above, so a script implements only what
    it uses -- and the runtime reports the provided set to the engine so absent
    callins cost nothing.

C2. Registration, per game

    pub fn script_for(def_name: &str) -> Option<Box<dyn UnitScript>> {
        match def_name {
            "gravit"   => Some(Box::new(Gravit::default())),
            "gate"     => Some(Box::new(Gate::default())),
            "crate"    => Some(Box::new(Crate::default())),
            "wall1"    => Some(Box::new(Wall::new(1))),
            ...
            _ => None,
        }
    }

    The rules-synced guest calls cus::runtime::unit_created(unit_id, def_id) from
    its existing unit_created callin, which looks up script_for(def_name), calls
    the create-script callout with the provided-callin mask, and starts Create in
    a thread. Destruction hooks into unit_destroyed.

C3. Migration order (per game)
    1. Land the engine surface; verify with one trivial script (wall1.lua is 14
       lines -- a good first target).
    2. Port the simple immobile scripts (wall1-4, plate, barrel, canister).
    3. Port the animated ones (gate, crate, electrafi, fire, projector).
    4. Port gravit.lua last -- it is the largest, uses PlayAnimation/toolKit.lua
       and the animations/ directory, and needs the anim toolkit ported too.
    5. Delete LuaRules/Gadgets/unit_script.lua and scripts/*.lua for that game.

    Gravitas is the natural first game: 5116 lines across 17 scripts, and its
    rules/UI are already Rust. Hunted-wasm is the natural second.

C4. Per-game cost estimate (Gravitas)
    wall1-4, plate            ~14 lines each, trivial
    barrel, canister          small, Explode-heavy
    gate, crate, electrafi,
    fire, projector*          moderate, Turn/Move/Sleep sequences
    gravit                    large, animation toolkit dependency
    toolKit.lua + animations/ must be ported before gravit

4. PARITY CHECKLIST (review against this)
--------------------------------------------------------------------------------

    [ ] All 40 LuaScriptNames callins reachable
    [ ] Synchronous return values honoured (QueryWeapon, AimFromWeapon,
        QueryTransport, QueryNanoPiece, QueryBuildInfo, BlockShot, TargetWeight,
        QueryLandingPads)
    [ ] Sleep uses floor(ms/33), minimum 1 frame
    [ ] StartThread runs immediately, inherits signal_mask
    [ ] Signal: bitmask AND for numbers, equality for non-numbers
    [ ] Signal only kills sleeping/waiting threads
    [ ] WaitFor* consult the engine's needsWait first
    [ ] Wait keys are piece*3+axis (move/turn), piece (scale)
    [ ] *Finished wakes all queued threads, tolerant of concurrent mutation
    [ ] Killed always calls SetDeathScriptFinished, including on error
    [ ] AimWeapon result -> aimReady weapon state
    [ ] AimShield result -> shield state
    [ ] Create started by the framework, not the engine
    [ ] Exactly the gadget's thread_wrap set is thread-wrapped
    [ ] Per-weapon NameN dispatch with the documented default return values
    [ ] Weapon indices 1-based
    [ ] Deterministic iteration order everywhere (sync safety)
    [ ] CallAsUnit equivalent works: a rules guest can invoke a named script
        entry point on a chosen unit, with args and return values
    [ ] Scripts can expose custom entry points beyond the 40 engine callins
    [ ] Killed settles from C++ even when the guest is missing, faulted, or
        never calls SetDeathScriptFinished
    [ ] Module unload detaches every live script before the handle dies
    [ ] Idle units cost zero per frame (no per-unit tick, no all-unit scan)

--------------------------------------------------------------------------------
5. OPEN QUESTIONS FOR REVIEWERS
--------------------------------------------------------------------------------

    1. SAVE/LOAD FIRST. Is CUS allowed to be non-saveable in v1? This single
       answer decides the scheduler (2B): yes -> async (A), no -> state machines
       (B) then proc macro (C). Nothing else should be decided before it.

    2. usMemBuffer: keep CNativeUnitScript within sizeof(CLuaUnitScript), or grow
       the per-unit inline buffer? Growing costs memory on every unit in every
       game, including ones not using CUS.

    3. Re-entrancy guard: which callins are allowed to be queued, and which must
       hard-reject during re-entrant execution because their C++ caller needs a
       synchronous result?

    4. CallFunctionByName: lift onto CUnitScript as a virtual, or introduce a
       small shared interface that CLuaUnitScript and CNativeUnitScript both
       implement? The latter avoids touching the COB path.

    5. Should CUS support mixed games (some units COB/LUS, some CUS)? The
       attachment model gives it for free; worth confirming it is wanted, since
       call-unit-script would then need to work across both.

    6. Timer wheel size: 256 buckets covers ~8.5s of sleep at 30Hz before
       overflow. Is that the right cut for real scripts?
