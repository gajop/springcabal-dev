Follow the evidence, not the language label

Why can either version be faster?

Both versions hand most world simulation and rendering to the same native engine. Lua calls native functions directly through its API. Rust executes compiled Wasm and crosses a typed host boundary for engine access. Rust can save interpreter, table and allocation work; it can also lose that gain to tiny imports, serialization, extra engine work or a different rendering workload.

Hunted: fixing extra work mattered more than syntax.

The first Rust port left per-team global LOS disabled while Lua enabled it. That caused extra native LOS raycasting. Restoring the same setting removed that cost. The subsequent pass uses a spatial food index, scalar Lua movement and cached Rust static surroundings. At 10×, Rust now spends much less time in both simulation and drawing.

That result supports efficient compiled game logic and fewer temporary data structures; it does not isolate a language constant. Startup input timing can change the first wave’s random sequence, so the recorded paths and later populations are not guaranteed equal.

Rust snapshot cache ↗

Flove: the dense scene is largely an engine workload.

Lua’s targeting now snapshots eligible targets once per AI tick, reuses weights and avoids copying command queues. Both renderers cache wisp geometry across passes. Rust’s dense scene is faster, but its host imports consume much more time than its remaining Wasm-only work. Rewriting arithmetic again cannot remove native collision, weapon or drawing costs.

Both target selectors preserve candidate order and random draw order. A nearest-target spatial index alone is not an equivalent replacement for weighted selection over every eligible target. Rust also retains its animated outlines and hover highlight.

Targeting and jobs code ↗

To the Last Drop: Lua’s advantage is mostly outside Wasm callbacks.

At 10× with shadows on in both, mean drawing is about 10.6 ms for Lua and 20.8 ms for Rust in the saved timing runs. All Rust callbacks, simulation and drawing combined, account for about 2.3 ms, including 1.0 ms in imports. Faster Wasm arithmetic cannot explain away the roughly 11 ms total gap.

The separate CPU profiles contain NVIDIA-driver samples under IStreamBufferConcept::WaitBuffer. The pinned engine loops around glClientWaitSync to wait for a buffer’s GPU fence before reuse. At 10×, roughly 20% of sampled Lua main-thread CPU and 18% of Rust main-thread CPU have that visible ancestor. This demonstrates waits in those captures, not the cause of the original gap. Another engine shared the GPU, and the instrumented timing direction reversed.

It is not justified to call TTLD finished. The next test should isolate shadow/model streaming costs while keeping positions, poses and visual settings fixed, rather than remove an effect and declare the language faster.

Area 17: fewer scans and crossings, modest whole-game gain.

Both ports now query nearby civilians once and retain the original ordered, strict base-position fear test. Rust’s normal per-frame import median fell from 1,037 to 59 in the optimization experiment. Much of the remaining scene cost is native unit movement and drawing, so the whole-frame win is smaller than the reduction in API calls.

The useful stress case is 2×. The attempted 10× Lua run hit its allocation ceiling, while Rust hit unit creation limits. Those failed scenes are not included as successful benchmarks.

Rust game source ↗

Gravitas fire: fewer host calls plus compiled particle work.

Lua caches expression factories while giving each particle a fresh mutable environment. Rust streams packed flame/smoke vertices into reusable native buffers. At ten emitter pairs, the previous per-vertex implementation made 35,558 drawing imports per frame; the final serial renderer makes 2,804. That change has a measured benefit, and the existing fire image comparison checks that the look is retained.

One emitter pair is close enough that the paired interval crosses a tie. At ten pairs, Rust’s advantage is clear. At 100 pairs, Rust’s existing 32,768-particle cap differs from the uncapped Lua fixture: that is not an equal-particle language comparison.

Why these jobs do not win at pool width four.

The released API copies input/output packets and instantiates a fresh private Wasmtime store per job. These kernels use immutable snapshots and ordered results; RNG, commands and mutations stay on the original thread. There is real parallel work, but also packing, dispatch, joining and result application.

Hunted’s small light calculation cannot repay that cost. Flove parallelizes target statistics, not the expensive native combat. Fire shifts billboard math to workers, but still transfers records and expands vertices on the caller. The one-thread experiment exposes much of this overhead without a parallel execution benefit. Four threads recover some of it, but do not deliver a clear overall win here.

Optimized is a claim about eliminated waste, not a finish line

What is already improved — and where to go next

There is concrete evidence of useful optimization: fewer API calls, fewer repeated scans and allocations, reused geometry, conservative visibility culling, and release LTO. The before/after tests retain state/event checks where applicable, plus existing pose and image comparisons. That supports “substantially optimized.” It does not establish optimal algorithms, renderer parity or a hardware ceiling.

Reproduce and audit

Keep each kind of evidence in its place.

Timings

Five alternating pairs; 300 warmup steps, 600 measured steps, one draw per step, 1024×736, VSync off, sound off. Both members of a pair are excluded if either fails or crosses the CPU-pressure threshold. One Flove pair is excluded.

World recordings

Fresh runs with a read-only observer, derived from Ship Game’s recording approach. All observed units and sampled projectiles are retained. They show workload and movement; serialization makes them unsuitable timing baselines.

CPU sampling

Fresh runs without the world observer. Linux perf samples user CPU at 499 Hz with DWARF stacks and JIT names. Sampling perturbs execution; stack proportions diagnose hot paths, rather than replace paired timings.

The engine and SDK remain pinned to release 2026.10.25. NVIDIA hardware rendering is required; the existing runner rejects llvmpipe and other software renderers. The cgroup pressure guard retains both global and local readings and fails closed. It does not certify exclusive GPU access.

Native work and visible output are not identical across all ports. Flove retains Rust-only visual improvements; Hunted startup decisions can vary; TTLD uses shadows on in both selected controls; the 100-emitter fire row has unequal particle caps. The scene lab exposes populations and traces alongside the times.
